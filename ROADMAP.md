# Roadmap

Здесь фиксируются запланированные улучшения. Текущая версия — MVP.

---

## v1.1 — Голосовые сообщения

**Задача:** Принимать голосовые сообщения и транскрибировать их в текст перед передачей в LLM.

**Реализация:**
- Скачать `.ogg` через Telegram Bot API
- Транскрибировать через [OpenAI Whisper API](https://platform.openai.com/docs/api-reference/audio/createTranscription) (или локальный whisper)
- Добавить переменную `WHISPER_MODEL` / `WHISPER_BASE_URL` в конфиг
- Поддержать голосовые как в прямых сообщениях боту, так и в replied message

**Текущий статус:** заглушка — бот отвечает "Голосовые сообщения пока не поддерживаются."

## v1.2 — Мультирепозиторий

**Задача:** Один бот — несколько GitHub репозиториев.

**Реализация:**
- Пользователь указывает проект ключевым словом или названием: `@bot задача для leash-system: ...`
- LLM определяет проект из контекста, если явно не указан
- Если проект неоднозначен — бот уточняет: "Вы имеете в виду `leash-system` или `bell-sensors`?"
- Маппинг `проект → owner/repo` хранится в конфиге или в БД
- Команда `/setrepo project owner/repo` для администраторов группы

## v1.2.1 — Память проектов / контекст репозитория

**Задача:** Дать боту минимальную долговременную память о проектах, чтобы LLM лучше понимала домен, стек, ограничения и смысл задач.

**Реализация:**
- Хранить краткий профиль проекта в отдельном файле или реестре
- Для каждого проекта описывать: `project_key`, `repo`, краткое описание продукта, стек, доменные сущности, архитектурные ограничения
- Подмешивать этот контекст в `system`/`user` prompt при `is_issue`, `preview` и `edit`
- Позже перевести память в машиночитаемый формат для мультирепозитория

**Зачем:**
- Меньше галлюцинаций по домену
- Лучше понимание legacy-ограничений
- Более точные issue-превью без длинных ручных пояснений в каждом сообщении

## v1.3 — Работа с существующими issues

**Задача:** Управлять issues после создания — комментировать, закрывать, обновлять, искать.

**Реализация:**

### Комментарии
- `@bot прокомментируй #123: ...` — добавить комментарий к issue
- `POST /repos/{owner}/{repo}/issues/{number}/comments`

### Закрытие
- `@bot закрой #123` — закрыть issue
- `@bot закрой #123: причина...` — закрыть с комментарием
- `PATCH /repos/{owner}/{repo}/issues/{number}` (`state: closed`)

### Обновление
- `@bot обнови #123: поправь заголовок / добавь метку / измени описание`
- LLM интерпретирует инструкцию → `PATCH` нужных полей

### Поиск
- `@bot найди issue про авторизацию` — поиск по заголовку/тексту среди открытых issues
- `GET /repos/{owner}/{repo}/issues` + фильтрация + LLM-ранжирование релевантности
- Бот выводит список: `#123 — Заголовок issue`

## v1.3.2 — Гибридный роутинг команд через LLM

**Задача:** Бот должен лучше понимать свободные формулировки и неявные просьбы, связанные с issues, не теряя при этом предсказуемость на простых командах.

**GitHub issue:** [#1](https://github.com/dmitryturin-art/issue-strategy-agent/issues/1)

**Идея:**
- Оставить быстрые детерминированные правила для очевидных случаев: `approve`, reply-редактирование, `закрой #123`, явный список `открытых issue`
- Для неоднозначных и разговорных формулировок включать LLM-роутер, который выбирает нужное действие: `new_preview`, `search`, `comment`, `close`, `reopen`, `update`, `clarify`
- LLM должен не просто классифицировать текст, а возвращать нормализованную команду с аргументами и уровнем уверенности

**Примеры формулировок, которые нужно понимать:**
- `посмотри, есть ли уже такая задача`
- `покажи, что сейчас открыто по карте`
- `можно закрыть это как неактуальное`
- `в этой задаче надо поправить описание`
- `есть что-то похожее про логин?`

**Реализация:**
- Ввести отдельный слой `intent router` перед основным dispatch
- Договориться о JSON-контракте от LLM:
  `action`, `issue_number`, `search_query`, `instruction`, `state_filter`, `confidence`, `needs_clarification`
- Добавить порог уверенности:
  при высокой уверенности выполнять действие, при низкой — задавать короткий уточняющий вопрос
- Передавать в LLM краткий список доступных действий и примеры фраз, чтобы модель выбирала из реальных возможностей бота
- Логировать спорные кейсы и собирать коллекцию реальных формулировок из чата для дальнейшего улучшения prompt/эвристик

**Принцип:**
- LLM помогает понимать язык пользователя, но не заменяет полностью deterministic-ветки
- Явные команды и критичные сценарии должны оставаться быстрыми и предсказуемыми

## v1.3.3 — Полноценная работа с комментариями issue

**Задача:** Дать боту полный и удобный цикл работы с комментариями в существующих issues.

**Реализация:**
- Добавить просмотр комментариев issue:
  - `@bot покажи комментарии #123`
  - `GET /repos/{owner}/{repo}/issues/{number}/comments`
- Добавить редактирование комментария:
  - `@bot измени комментарий 456 в #123: ...`
  - `PATCH /repos/{owner}/{repo}/issues/comments/{comment_id}`
- Добавить удаление комментария:
  - `@bot удали комментарий 456`
  - `DELETE /repos/{owner}/{repo}/issues/comments/{comment_id}`
- Добавить более удобный UX для выбора комментария, если пользователь не знает `comment_id`
  - показать последние комментарии с короткими ID/ссылками
  - дать команду вида `@bot удали последний мой комментарий в #123`
- Поддержать LLM-разбор разговорных формулировок для comment workflows

**Зачем:**
- Сейчас бот умеет только добавлять комментарии
- Для реальной рабочей переписки нужны просмотр, правка и удаление
- Это уменьшит необходимость переключаться в GitHub ради мелких правок

## v1.3.4 — Вложения и изображения

**Задача:** Улучшить работу бота с изображениями и другими вложениями как при создании issue, так и при дальнейшей работе с ними.

**Текущее состояние:**
- Фото из Telegram уже передаются в LLM как vision-input при создании preview
- Бот умеет учитывать скриншот из текущего сообщения и из replied message
- Вложения пока не сохраняются и не публикуются как полноценные артефакты в GitHub issue

**Реализация:**
- Явно поддержать сценарии:
  - несколько изображений в одном обращении
  - изображение + текст
  - reply на сообщение с изображением
- Продумать, как отражать изображения в итоговом GitHub issue:
  - ссылки на Telegram-file URL недолговечны, их нельзя считать надежным хранилищем
  - нужен отдельный способ публикации/хранения изображений, если хотим видеть их прямо в issue
- Рассмотреть поддержку других типов вложений:
  - документы
  - файлы логов
  - видео / gif
- Добавить понятный UX, если пользователь прислал вложение неподдерживаемого типа

**Зачем:**
- Скриншоты и визуальные баги — частый сценарий для issue-бота
- Сейчас изображения помогают LLM понять задачу, но не становятся частью GitHub issue как артефакт
- Полноценная поддержка вложений сильно повысит практическую ценность бота

## v1.3.5 — Разговорный assistant-mode по @mention

**Задача:** Если пользователь явно обращается к боту, но это не команда и не запрос на работу с issue, бот должен уметь отвечать как обычный LLM-ассистент по тексту, скриншоту или replied message.

**GitHub issue:** [#3](https://github.com/dmitryturin-art/issue-strategy-agent/issues/3)

**Идея:**
- Сохранить жёсткий приоритет для deterministic-веток:
  - approve
  - edit preview
  - comment / close / reopen / update / search
  - явные issue-команды
- Если это не issue-сценарий, но есть явный `@mention`, передавать сообщение в assistant-mode вместо ответа `Похоже, это не задача для issue`

**Примеры сценариев:**
- `@bot что видишь на скриншоте?`
- `@bot как это лучше сделать?`
- `@bot что скажешь по этому экрану?`
- reply на сообщение пользователя с картинкой: `@bot это нормальный UX?`
- `@bot надо сделать так же` с replied context

**Правило trigger/mention:**
- Reply сам по себе не должен включать assistant-mode
- Для assistant-mode, как и для остальных действий, нужен явный `@mention`
- Это защищает от ложных срабатываний, когда пользователь просто отвечает другому участнику чата

**Целевой порядок роутинга:**
1. `system actions`
   - `/task`, `/issue`, `/add`
   - approve
   - edit preview
   - pending search state
2. `deterministic issue actions`
   - явный search/list issues
   - comment / close / reopen / update
3. `LLM intent router`
   - `issue_create`
   - `issue_search`
   - `issue_comment`
   - `issue_close`
   - `issue_reopen`
   - `issue_update`
   - `assistant_reply`
   - `clarify`
   - `ignore`
4. `assistant-mode`
   - включается только при явном `@mention`, если issue-flow не распознан

**Реализация:**
- Добавить новый тип действия/маршрута: `assistant_reply`
- Разделить LLM-routing на два слоя:
  - issue-oriented intent routing
  - fallback assistant-mode для явного @mention
- Продумать prompt для assistant-mode:
  - отвечать по делу
  - учитывать текст, replied context и изображения
  - не пытаться без необходимости превращать ответ в issue
- Добавить защиту от путаницы:
  - жёсткие команды и issue flows всегда выше по приоритету
  - assistant-mode включается только если явный mention есть, но issue-сценарий не распознан
  - reply без mention не должен запускать assistant-mode

**Технический план по файлам:**
- `app/bot.py`
  - ввести явную ветку `assistant_reply`
  - сохранить приоритет текущих deterministic-веток
  - вызывать assistant handler только после неуспешного issue-routing
- `app/llm.py`
  - расширить router до полного выбора маршрута, а не только issue-intent
  - добавить отдельный prompt для assistant-mode
  - использовать text + replied_text + images_b64 для ответа
- `app/trigger.py`
  - сохранить правило: без явного `@mention` assistant-mode не включается
  - не расширять trigger до “любой reply”, чтобы бот не путался в обычной групповой переписке
- `docs/ARCHITECTURE.md`
  - после реализации обновить схему message flow и выделить 3 режима: system / issue / assistant
- regression-check
  - проверить явные issue-команды
  - проверить assistant-вопрос по тексту
  - проверить assistant-вопрос по скриншоту
  - проверить reply на пользовательское сообщение с картинкой + `@mention`
  - проверить, что reply без mention не активирует бота

**Кейсы, где лучше уточнять, а не угадывать:**
- `@bot надо сделать так же`
- `@bot это сюда`
- `@bot посмотри`

В таких случаях, если намерение неочевидно, бот должен спросить:
- оформить это как issue
- или просто ответить как ассистент

**Зачем:**
- Иногда пользователю нужен не issue, а просто ответ по скриншоту или контексту
- Это делает бота полезнее в реальном рабочем чате
- При жёстком приоритете команд бот не должен начать путаться между “задай вопрос” и “создай issue”

## v2.3 — Agent memory и reusable skills для сопровождения проекта

**Задача:** Сократить повторное чтение контекста, ускорить сопровождение проекта и уменьшить расход токенов за счет проектной памяти и переиспользуемых skills/workflows.

**Реализация:**
- Держать короткий индекс `AGENTS.md` и маленькие тематические файлы в `docs/agent/`
- Выносить повторяющиеся operational workflows в отдельные markdown-файлы или skills
- Для часто повторяющихся сценариев предлагать:
  - новый локальный skill
  - установку подходящего существующего skill
  - компактные шаблоны для debugging, GitHub triage, restart/smoke-check
- Не раздувать один общий агентский файл, а использовать ссылочную структуру с маленькими документами

**Зачем:**
- Меньше лишнего контекста в каждой сессии
- Быстрее вход в проект после паузы
- Более стабильная работа агента на повторяющихся задачах
