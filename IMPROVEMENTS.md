# Предложения по улучшению

Сформированы 2026-05-27 на основе анализа кодовой базы и документации проекта `issue-strategy-agent`.
Сгруппированы по категориям: быстрые, архитектурные, продуктовые, надёжность, безопасность.

То, что уже запланировано в [ROADMAP.md](ROADMAP.md), не дублируется.

## 1. Быстрые улучшения (низкая стоимость, высокий эффект)

### 1a. Structured output / JSON mode для LLM

Сейчас `_extract_json()` выдирает JSON регуляркой `re.search(r"\{.*\}", raw, re.DOTALL)`, и это нестабильно — LLM может обернуть ответ в текст, добавить лишние скобки или вернуть сломанный JSON.

**Решение:** использовать `response_format: {"type": "json_object"}` (OpenAI-совместимые API) или `json_schema` (OpenRouter). Это гарантирует валидный JSON и позволяет убрать хрупкий regex-парсинг.

**Файлы:** `app/llm.py` — `_call_llm()` и `_extract_json()`.

### 1b. Retry с backoff при сбоях парсинга JSON

Даже с JSON mode иногда LLM возвращает мусор. Сейчас падает сразу. Стоит сделать 1-2 retry с тем же запросом.

### 1c. Chat action («печатает...») перед LLM-запросами

При вызове LLM (особенно с изображениями) пользователь ждёт 2-5 секунд в тишине. `bot.send_chat_action(chat_id, "typing")` — 2 строки кода, UX сильно лучше.

**Файлы:** `app/bot.py` — перед каждым вызовом LLM.

### 1d. Обрезка слишком длинных сообщений

Если пользователь присылает 3000+ символов, LLM-запрос раздувается. Обрезать `user_prompt` до ~2000 символов с пометкой `[обрезано]` и логированием.

**Файлы:** `app/llm.py` — `_build_content()` или `check_is_issue()`/`generate_preview()`.

### 1e. Команда `/cancel`

Удалить preview (и запись в БД) без создания issue. Сейчас preview висит, пока его не аппрувят.

**Файлы:** `app/bot.py`, `app/storage.py` — метод `delete_task()`.

## 2. Архитектурные улучшения

### 2a. Разделение роутинга и handler'ов

`bot.py` уже 461 строка и продолжит расти (v1.3.2 добавит intent router, v1.3.5 — assistant mode).

**Предлагаемая структура:**

```
app/
  router.py         ← dispatch: кто обрабатывает это сообщение?
  handlers/
    preview.py      ← _handle_new_preview, _handle_edit, _handle_approve
    issues.py       ← _dispatch_issue_intent и все _handle_issue_*
    commands.py     ← /start, /help, /cancel, /report
```

Облегчит тестирование, уменьшит размер файлов, упростит добавление новых режимов.

### 2b. Простой DI для тестируемости

Все зависимости — глобальные импорты (`from app.llm import ...`). Для unit-тестов это неудобно.

**Решение:** лёгкий DI-контейнер:

```python
# app/deps.py
class Dependencies:
    llm: LLMService
    github: GitHubClient
    storage: Storage
```

Без тяжёлых фреймворков, просто прокидывать в handler'ы.

### 2c. Кэширование `check_is_issue` по хешу текста

Одинаковые сообщения приходят часто. Кэшировать результат с TTL 5 минут по хешу нормализованного текста — снизит расходы на LLM.

## 3. Продуктовые улучшения

### 3a. Просмотр деталей конкретного issue: `@bot покажи #123`

Бот умеет искать списком, но не умеет показать один issue с заголовком и статусом. `get_issue()` уже есть в `github_client.py`, нужен только handler.

### 3b. Валидация меток (labels)

LLM предлагает любые метки, включая несуществующие. При старте загружать список реальных меток через `GET /repos/{owner}/{repo}/labels`, показывать их в промпте и фильтровать предложенное.

**Файлы:** `app/github_client.py` — новый метод `get_labels()`; `app/llm.py` — добавить в промпт; `app/bot.py` — фильтрация.

### 3c. Пагинация в результатах поиска

`search_issues` и `list_issues` ограничены 100 результатами. Добавить параметр `page` и отдавать по 10-15 результатов, либо команду `@bot ещё`.

### 3d. `/report` или `@bot статистика`

Быстрый отчёт: «создано 12 issue за неделю, 5 открыто, 7 закрыто». Данные уже есть в БД.

**Файлы:** `app/bot.py` — новый handler; `app/storage.py` — метод `get_stats()`.

## 4. Надёжность и observability

### 4a. Health-check endpoint

Встроить простой HTTP-сервер на `aiohttp` внутри event loop бота. 15 строк кода, а мониторинг через UptimeRobot или systemd становится тривиальным.

**Файлы:** новый `app/health.py`; `app/main.py` — запуск рядом с polling.

### 4b. Graceful shutdown

Сейчас бот падает по сигналу без завершения операций. Перехватывать `SIGTERM`/`SIGINT`, вызывать `dp.stop_polling()` и закрывать `httpx.AsyncClient`.

**Файлы:** `app/main.py`.

### 4c. Метрики в логах

Структурированные счётчики: количество успешных/неуспешных LLM-запросов, созданных issue, latency. Хотя бы через `logger.info` с префиксом `[METRIC]` для парсинга через `journalctl | grep METRIC`.

### 4d. Бэкап SQLite

Раз в день или при остановке — копировать `data/bot.db` в `data/bot.db.bak`. Или команда `@bot backup` для администратора.

## 5. Безопасность и защита от злоупотреблений

### 5a. Rate limiting на пользователя

Хранить счётчик preview в час на `user_id`, при превышении — игнорировать.

**Файлы:** `app/bot.py` — проверка перед `_handle_new_preview()`.

### 5b. Сжатие изображений перед отправкой в LLM

Фото из Telegram могут быть 4000×3000 px. Сжимать до max 1024px по большей стороне через Pillow перед base64-кодированием — снизит токены на vision-запросы в 5-10 раз.

**Файлы:** `app/bot.py` — `_download_photo()`.

### 5c. Санитизация спецсимволов GitHub search

`normalize_issue_search_query` не чистит спецсимволы поиска GitHub (`:`, `!`, `@`). Экранировать или вырезать их.

**Файлы:** `app/trigger.py` — `normalize_issue_search_query()`.
