# Agent System Blueprint

## Что это такое

Это переносимый blueprint проектной памяти для Codex-подобного агента. Его можно скормить новому проекту как стартовую идеологию, чтобы агент:

- быстрее входил в контекст после новой сессии
- меньше тратил токены на повторное чтение одних и тех же файлов
- накапливал рабочую память маленькими тематическими файлами
- переиспользовал локальные skills для повторяющихся сценариев

## Главный принцип

Не делать один огромный агентский файл.

Вместо этого:
- `AGENTS.md` хранит только короткий индекс и базовые принципы
- подробности лежат в маленьких файлах `docs/agent/*.md`
- повторяемые многошаговые сценарии выносятся в локальные skills в `.codex/skills/`

## Базовая структура

```text
AGENTS.md
docs/
  agent/
    session-start.md
    communication.md
    runtime.md
    workflow.md
    commands.md
    tracking.md
    github.md
    debugging.md
    self-improvement.md
    agent-system-blueprint.md
.codex/
  skills/
    bot-restart-smoke-check/
    issue-triage/
    github-followup-draft/
    bot-debug-routing/
```

## Роли файлов

### `AGENTS.md`

Короткий индекс:
- какие агентные файлы существуют
- что открыть в первую очередь
- 3-5 базовых принципов проекта

Не превращать его в длинную энциклопедию.

### `docs/agent/session-start.md`

Сверхкороткий старт новой сессии:
- что открыть за 30 секунд
- что важно быстро вспомнить
- какие локальные skills уже есть

### `docs/agent/communication.md`

Правила языка и стиля:
- на каком языке общаться
- на каком языке писать issue, roadmap, worklog, user-facing тексты
- какой тон и плотность ответа предпочтительны

### `docs/agent/runtime.md`

Операционная память:
- где корень проекта
- какое окружение
- как запускать
- чем проверять код

### `docs/agent/workflow.md`

Типовой рабочий цикл:
- что читать в начале
- как проверять изменения
- когда перезапускать
- когда делать живой smoke-check

### `docs/agent/commands.md`

Частые команды:
- запуск
- проверка
- git
- sqlite
- типовые grep/rg

### `docs/agent/tracking.md`

Когда фиксировать follow-up:
- что писать в roadmap
- что выносить в GitHub issue
- когда готовить draft issue

### `docs/agent/github.md`

Локальная идеология работы с backlog:
- как не плодить дубли
- как писать заголовки и описания issue
- как оформлять draft issue

### `docs/agent/debugging.md`

Типовой playbook диагностики:
- где искать источник проблемы
- как идти по цепочке роутинга
- как проверять регрессии

### `docs/agent/self-improvement.md`

Правила саморазвития агентной системы:
- когда достаточно маленького md-файла
- когда нужен новый skill
- когда стоит подтянуть существующий skill

## Когда добавлять новый markdown-файл

Добавляй новый `docs/agent/*.md`, если:
- знание регулярно нужно в новых сессиях
- это не длинная документация, а компактная рабочая память
- это помогает не перечитывать полпроекта ради одной процедуры

## Когда добавлять новый skill

Добавляй локальный skill, если:
- сценарий повторяется в разных сессиях
- у него есть устойчивый набор шагов
- нужен узкий контекст, который не хочется каждый раз восстанавливать
- skill реально сокращает токены и время

## Минимальные правила для локального skill

У skill должен быть:
- `SKILL.md`
- при необходимости `references/`
- желательно `agents/openai.yaml`

Skill должен быть:
- коротким
- прикладным
- не дублировать полпроекта
- ориентированным на конкретный workflow

## Как переносить эту систему в другой проект

1. Скопировать `AGENTS.md`.
2. Скопировать папку `docs/agent/`.
3. Переписать:
   - язык общения
   - runtime и команды запуска
   - workflow проекта
   - backlog/GitHub правила под конкретную команду
4. Перенести только те локальные skills, которые реально подходят новому проекту.
5. В первой же сессии обновить `session-start.md` и `runtime.md` под новый репозиторий.

## Что не надо делать

- Не хранить все в одном giant prompt-файле.
- Не дублировать одно и то же знание в пяти местах.
- Не создавать skill на каждую мелочь.
- Не делать skills, которые описывают слишком общий процесс без реальной пользы.

## Хорошая эволюция системы

Нормальный порядок роста такой:

1. Появилась повторяющаяся проблема.
2. Появился маленький `docs/agent/*.md`.
3. Проблема стала регулярной и многошаговой.
4. Появился локальный skill.
5. Если skill реально полезен многим проектам, его можно обобщить и вынести отдельно.

## Что обновлять по ходу жизни проекта

Обновляй систему, когда:
- поменялся способ запуска
- поменялся рабочий цикл
- появились новые устойчивые типы задач
- агент начал повторять одни и те же лишние действия
- выяснилось, что какой-то skill не экономит, а только засоряет контекст

## Практический use case

Если в новом проекте после старта новой сессии агент “тупит”, долго вспоминает запуск, ищет рабочие команды и теряет follow-up идеи, значит blueprint стоит развернуть и заполнить минимальные файлы:

- `AGENTS.md`
- `docs/agent/session-start.md`
- `docs/agent/runtime.md`
- `docs/agent/workflow.md`
- `docs/agent/tracking.md`

Этого уже достаточно, чтобы резко улучшить стабильность новой сессии.
