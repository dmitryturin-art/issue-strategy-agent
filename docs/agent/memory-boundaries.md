# Memory Boundaries

## Зачем это нужно

В проекте есть несколько разных слоев памяти. Их нельзя смешивать, иначе агент начнет путать:
- как устроен сам продукт
- как устроен процесс разработки
- как устроена собственная рабочая память агента

## 1. Память продукта / самого бота

Это память о том, как работает бот как система для конечных пользователей.

Сюда относятся:
- `ROADMAP.md`
- `docs/WORKLOG.md`
- `docs/ARCHITECTURE.md`
- `docs/PROJECT_MEMORY.md`
- код в `app/*`

Это источник правды про:
- поведение бота
- product UX
- архитектуру
- интеграции
- доменную логику

## 2. Память среды разработки и сопровождения

Это память не про пользователя бота, а про то, как правильно сопровождать этот репозиторий.

Сюда относятся:
- `AGENTS.md`
- `docs/agent/*.md`
- `.codex/skills/*`

Это источник правды про:
- как запускать проект
- как перезапускать бота
- как делать smoke-check
- как работать с GitHub этого репозитория
- какие локальные workflows и agent skills уже есть

## 3. Память о целевых внешних репозиториях бота

Это отдельный слой, который относится к тем GitHub-репозиториям, с которыми работает сам бот как продукт.

Например:
- `GITHUB_DEFAULT_REPO` в `.env`
- проектные профили в `docs/PROJECT_MEMORY.md`
- логика в `app/github_client.py`

Это не то же самое, что сопровождение репозитория `issue-strategy-agent`.

## Практическое правило

- Если информация нужна для разработки и сопровождения этого репозитория, она должна жить в `AGENTS.md`, `docs/agent/*` или `.codex/skills/*`.
- Если информация описывает поведение бота как продукта, она должна жить в product/docs/code слое.
- Если информация относится к внешним репозиториям, с которыми бот работает по бизнес-логике, не надо смешивать ее с GitHub workflow самого `issue-strategy-agent`.

## Антипаттерн

Плохо:
- хранить правила запуска проекта рядом с продуктовой доменной памятью
- смешивать токены и доступы бота с доступами разработческой среды
- записывать agent workflow как будто это часть поведения самого бота

Хорошо:
- продуктовая память отдельно
- agent/developer memory отдельно
- внешний GitHub/business context отдельно
