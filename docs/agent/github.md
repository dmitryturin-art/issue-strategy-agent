# GitHub Workflow

## Когда заводить issue

- Если договоренность уже превратилась в конкретную рабочую задачу, ее стоит отслеживать не только в чате и не только в `ROADMAP.md`, но и в GitHub issue.
- Если задача влияет на продуктовый roadmap, сначала зафиксировать ее в `ROADMAP.md`, затем создать issue или хотя бы draft issue.
- Если идея пока сырая и пользователь не просил трекать ее как задачу, не нужно автоматически плодить issues.

## Как избегать дублей

Перед созданием новой задачи быстро проверить:
- `ROADMAP.md`
- `docs/WORKLOG.md`
- текущие открытые issues

## Как оформлять

- Заголовок делать коротким и конкретным.
- Описание делать прикладным: проблема, ожидаемое поведение, зачем это нужно, возможные шаги реализации.
- Все тексты issue по умолчанию писать на русском языке.

## Какой доступ использовать

- Для работы с GitHub этого репозитория использовать стандартную авторизацию, уже подключенную к git/VS Code.
- Если `git push` работает, это и есть основной путь для операций сопровождения репозитория.
- Не использовать `GITHUB_TOKEN` из `.env` для административных действий по репозиторию `issue-strategy-agent`, если только пользователь явно не сказал обратное.
- `GITHUB_TOKEN` из `.env` относится к логике бота и его интеграции с целевыми репозиториями, а не к внутреннему обслуживанию этого репозитория.

## Если issue нельзя создать сразу

- Подготовить готовый draft:
  - заголовок
  - краткое описание
  - критерий завершения или ожидаемый результат
- В ответе явно отметить, что issue еще нужно создать отдельно.
